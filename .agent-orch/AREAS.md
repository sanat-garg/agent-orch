# Areas: per-feature notes

_Read the section for the area you touch; CONTEXT.md holds the cross-cutting rules. Module header comments explain each module's API. Keep entries to rules and gotchas, never history._

- Users (owner, 2026-10-04; `users.mjs`, `public/users.js`): accounts in data/users.json, migrated once from auth.json into the admin (id `admin`, alias `claude`, the old login page's hidden username, so saved passwords still work); a session without `user` is the admin's, so never invalidate those. `convos[].owner` (none = admin); a folder, and its tasks, schedules and files, belongs to its main chat's owner (server.mjs `pathOwner`). Non-admins pass `userBlocked` (an allowlist) and every ws message passes `forClient`; everyone's sidebar lists only their own chats (a user with `allProjects` sees every project: one switch, never per-project picks, owner 2026-10-15). A user may connect their own GitHub (`github-users.mjs`, Settings → Account: device code via gh's OAuth app, or a PAT): server.mjs `ghOf(dir)` makes a folder's new repo in its owner's account, and that repo's .git/config carries their gh credential helper + `agent-orch.github-user` (also what lets them open a folder they imported); unconnected users' projects go to the admin's GitHub. Caps are % of a weekly window (`<agent>/<window>`); a user's usage is the window's pct × their share of weighted tokens since it began (usage.mjs tokens records carry `user` and `model`). At a cap, chat sends are refused and the orchestrator's `userCap` makes their tasks wait or delegate like a limit.
- Chats (owner, 2026-10-03): a project folder can have many chats. Its **main chat** (server.mjs `mainChatId`: `projects.convo_id`, else the oldest) alone carries the project rank, orchestrator notes, task fallbacks/effort and the Live previews row; `ensureProject` never moves convo_id off a main chat that still exists, and deleting it hands the project to the next oldest chat. Repo/git state is per folder (`shareRepoState`). Never re-add the old boot fold that merged a folder's chats. Merging is owner-triggered only (POST /api/convos/:id/merge → server.mjs `mergeChat`: the log block is spliced in by `ts`, the main chat's next message carries `mergedRecaps`). Archive (`convos[].archived`, set on every chat of the folder) only hides the project in the sidebar and stops reflection (orchestrator `projectArchived`); tasks and schedules still run, and a new chat in the folder unarchives it.
- Sidebar order (owner, 2026-10-19, #2230): latest activity first, ties by name (app.js `byActivity`). `project.lastActivityAt` (ms) = orchestrator `activityMap` (one query over tasks/events/messages, bumped by logEvent/pushTask/deferMessage, pushed as ws 'oactivity') maxed with the folder's chats' updatedAt. The #510 drag order and POST /api/orch/projects/reorder are gone; orchestrator `reorderProjects` and projects.position/priority stay for the scheduler.
- Opening a chat (owner, 2026-10-12: up to 30 s on the phone) sends only its tail: `chat-log.mjs logWindow` reads the log backwards (~150–300 events, starting at a prompt, long tool I/O clipped with `cut`); the client draws only ~2 screens of it (app.js `backlogCut`, never between a tool call and its result) and the rest from `backlog` as the reader scrolls up (IntersectionObserver on `.history-more`), then `{t:'older', before: byte}` pages back. Never send the whole log in `history` again. The last 6 settled chats stay drawn (`chatCache`); reopening sends `since` = the view's `logMark` (`boot.gen.bytes`, carried by every `emit` and history frame) and gets only appended events (`logSince`). Any non-append log change must go through `writeLog`/`removeConvo` (they bump the generation) or a stale view is reused. A connection is sent a project's tasks once (`ws.orchSent`); `otask` frames keep them. Browser frames ≥16 KB are deflated. Tool cards build their body on first open (`fillTool`; a cut card fetches GET /api/convos/:id/tools/:toolId). Bulk task views go through orchestrator `withDeps` (graph loaded once): the per-task recursive `all_deps` query made a 400-task snapshot cost 700 ms.
- Chat token usage (owner, 2026-10-19; `chat-usage.mjs`, `public/tokens.js`), header pill + sidebar ⋯ → Token usage): lifetime totals per `chat:<cid>`/`task:<id>` live in data/metrics/token-totals.json (usage.mjs, rebuilt from usage.jsonl if missing; planner replies carry the chat via runAgent `chatRef`; merges move them). The CLIs report weekly limits only as %, so a week's size is estimated as weighted tokens recorded up to the reading ÷ its pct (none under 2%); never hardcode plan token limits.
- Freshness (owner, 2026-10-13; server.mjs `freshen`, github.mjs `pull`): opening a chat (or sending) when its folder's `git.checkedAt` is over an hour old fetches origin first and, if behind, merges it in (ff, else a merge commit; never rebase: chat logs hold commit shas) under `queueGit` + orchestrator `withRepo` (serialGit). Sends wait for it; the chat shows `{t:'gitpull'}` progress and a notice. A conflict changes nothing and is logged as an error. Skipped while a chat of the folder is mid-turn.
- Rewind/delete a prompt (owner, 2026-10-11; server.mjs `rewindChat`/`deletePrompt`, app.js `promptMeta`): a prompt is its `user` event's `ts`. Each chat turn's commit is logged as a hidden `{t:'commit', sha}` event (`chatSync`); rewind-with-code reverts those after the prompt as ONE new commit (github.mjs `revertCommits`, never reset/force, so task merges stay; conflict = nothing changes). Rewind drops the agent/planner session and the next message carries a recap (`takeMergedRecap`); delete keeps the session and tells it to disregard. Chat-only rewind and delete keep the commit events. Idle chats only. Edit (app.js `editPrompt`) is client-only: that rewind (code by default) then a normal `send` of the new text with the old upload ids.
- Credentials (owner, 2026-10-08; `credentials.mjs`, `public/credentials.js`, sidebar → Credentials): per-user service logins/keys, AES-GCM in data/credentials.json with data/credentials.key (lose the key = lose them; never regenerated over an existing file). Every route touches only `me.id`'s; a deleted user's move to the admin. Agents don't read them (yet). Projects write them (owner, 2026-10-13): every syncGitNow (and boot) imports the folder's .env secrets (`projectSecrets`: root + one dir down, secret-looking names only) into its owner's per-project card (`importProject`; `seen` hashes, so owner edits/deletes stick until the value changes). Task worktrees' and workers' .env files are never seen, so only the chat prompt tells agents to use .env.
