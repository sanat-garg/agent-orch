## Prompt

The owner wants concurrency decided by MEASURED performance, not fixed numbers (BRIEF goal 9). This builds on #299, which removed the pre-emptive memory gates and widened the caps; #299's values (controller 4, MacBook 10) become starting points and optional owner ceilings, and the default ceiling is 'Auto (none)' with a sanity maximum of 64. Implement capacity.mjs, an adaptive controller per node: 1) Signals, sampled every 5 s and smoothed: on Linux, PSI from /proc/pressure/cpu, memory and io (some/full avg10/avg60; e.g. live on the VPS right now: cpu some avg300≈43%), MemAvailable and swap, and the load per core; on macOS (sent by worker.mjs in telemetry), `sysctl -n kern.memorystatus_vm_pressure_level` (1 normal / 2 warn / 4 critical), vm.loadavg / hw.ncpu, the swap usage from `sysctl vm.swapusage`, and the compressor pages from vm_stat. Plus task-level signals for both: the rolling median time per tool call and per done_when check for running tasks on that node, compared with that node's baseline at low concurrency (a slowdown ratio), and agent process stalls (no event for more than N minutes while not waiting on the LLM). 2) Control loop (AIMD, like TCP congestion control): the target slot count starts at the node's learned best (persisted in the nodes table as learned_slots; default the #299 value). Every 2 min, if all signals are healthy (e.g. cpu PSI some avg60 < 60%, memory PSI some avg10 < 10% and full = 0, MemAvailable > 400 MB, mac pressure level 1, slowdown ratio < 1.5) AND there is ready work waiting, add 1 slot. On mild pressure, hold. On clear saturation (memory PSI full > 0, mac pressure ≥ 2, cpu PSI some avg10 > 90% for 30 s with slowdown > 2.5, or MemAvailable < 400 MB), cut the target by about 30% (at least 1), and if running > target, stop claiming (don't kill tasks) until it drains; the emergency brake from #299 still pauses the newest task near OOM. Update learned_slots as the highest target that stayed healthy for 15+ min (with slow decay). Thresholds live in CFG, tunable. 3) The scheduler uses min(adaptive target, the owner ceiling if set). The rapid-mode top-up (#300) uses these targets for 'free slots'. 4) Visibility: the Machines view shows per node 'Target 7 (learning ↑)', the key signals as small sparklines (CPU pressure, memory pressure, slowdown) and the last adjustment reason ('+1: healthy, 3 ready tasks' / '-2: memory pressure'). Settings: 'Concurrency: Adaptive (recommended) / Fixed N', plus the per-node optional ceiling. Also log adjustments as events. 5) Tests with synthetic signal sequences: ramps up under healthy signals with queued work; holds without work; cuts ~30% on memory pressure; learned_slots persists and seeds after a restart; the macOS pressure level parsing; the owner ceiling respected. Run only the touched test files.
